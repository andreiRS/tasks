# The visual board is a long-running local server that reuses the mutation core in-process

`tasks serve` starts a localhost-only HTTP server that imports the existing mutation core (`store.ts`, `queries.ts`, `validation.ts`) and calls it directly, so every write from the browser runs the same `flock → dirty-tree guard → Validator → commit` path as a one-shot CLI invocation. Reads are served as a board snapshot; live updates come from watching the Store directory (`fs.watch` → debounce → re-read → broadcast a full snapshot over Server-Sent Events), so a move committed by an agent's `tasks mv` appears on every open board within a moment. The React + dnd-kit frontend is built by Vite and embedded into the single compiled binary, so distribution stays a single self-contained `tasks` executable. The alternatives were: shelling out to the `tasks` CLI per action (rejected — pays process-startup cost per write and re-parses output the core already has in memory), and a desktop wrapper such as Tauri (rejected — adds a Rust toolchain and packaging, and cannot run the Bun core in-process). SSE was chosen over WebSocket because the traffic is one-way: writes go over plain POST/PATCH, the stream only carries snapshots.

This realizes the "library API that enforces the same invariants" that ADR-0002 deferred: the server is a second in-process caller of the sanctioned writer, not a second writer. The CLI remains the contract; the server reuses it rather than reimplementing it. It also qualifies ADR-0014's deliberately small dependency surface: the frontend toolchain (React, Vite, dnd-kit, a markdown renderer) is a meaningfully larger dependency set, accepted only because it is scoped to the `serve` subsystem and its build output, and never pulled into the core CLI paths. ADR-0014 stands unchanged for everything outside `serve`.

## Consequences

- The board and the CLI cannot disagree about what a write is allowed to do; there is exactly one lock/validate/commit implementation, and a browser drag produces the same single commit as the equivalent `tasks mv`.
- The server is bound to `127.0.0.1` with no authentication, on the same single-user, single-machine assumption as the rest of the tool. Remote access and auth are explicitly out of scope.
- Writes inherit the core's guards verbatim: a dirty Store rejects the write with `STORE_DIRTY`, and a long-held Lock (e.g. an agent mid-operation) blocks a browser write until it frees. The UI must surface these honestly rather than hide them.
- `fs.watch` on macOS can coalesce or miss events and fires on `.git`-internal writes; the debounce-and-rebroadcast-full-snapshot design absorbs this, at the cost of recomputing the whole snapshot on every change rather than diffing.
- The frontend dependency surface and a Vite build step now sit in the repo. They are confined to `serve`; the core CLI, its tests, and its compiled size are unaffected except for the embedded asset blob.
- The single-binary distribution (ADR-0014) is preserved only as long as Vite output is embedded at compile time; shipping assets as loose files would break it and is rejected.
